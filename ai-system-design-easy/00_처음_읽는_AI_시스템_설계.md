# 00. 처음 읽는 AI 시스템 설계

> **비개발자를 위한 AI 시스템 설계 입문서 · 00**  
> 이번 장의 질문: **AI는 질문을 받아서 어떻게 답을 만들고, 서비스를 만드는 사람은 그중 무엇을 알아야 할까?**

- 난이도: ★★☆☆☆ — 용어의 뜻과 역할만 이해하면 충분
- 예상 학습 시간: 15~20분
- 먼저 읽기: 없음 (시리즈의 첫 장)
- 참고 원문: [AI System Design Guide — LLM Internals](https://github.com/ombharatiya/ai-system-design-guide/blob/main/01-foundations/01-llm-internals.md)

> 이 글은 원문을 옮긴 번역본이 아니라, 원문의 핵심 개념을 초보자 눈높이에 맞춰 새로 풀어 쓴 **독립 해설**이에요. 모델별 최신 수치보다 원리와 서비스 설계 판단에 집중했고, 모든 모델이 같은 구조·캐싱 방식을 쓴다는 뜻은 아니에요.

---

## 먼저 상황 하나

내가 만든 웹사이트에 AI 답변 기능을 붙였다고 해 볼게요. 그런데 어떤 날은 답이 훌륭하고, 어떤 날은 엉뚱해요. 요금은 생각보다 많이 나오고, 대화가 길어지면 앞에서 한 말을 잊어버리기도 하죠.

이럴 때 "AI가 원래 그렇지 뭐" 하고 넘기면 고칠 방법이 없어요. 그렇다고 Transformer 논문부터 펼치면 서비스는 한참 뒤로 밀리고요.

이 장은 딱 그 중간을 잡아요. AI가 답을 만드는 흐름을 한 번 훑어보고, 자주 나오는 용어 다섯 개가 **내 서비스의 비용·속도·품질과 어떻게 연결되는지**만 짚어 볼게요. 수식이나 구현은 필요해질 때 공부해도 충분해요.

## 이 장을 읽고 나면

- AI가 질문을 읽고 답을 만드는 기본 흐름 설명하기
- Transformer, 토큰, Attention, KV Cache, MoE가 왜 나왔는지 이해하기
- API로 서비스를 만드는 사람이 지금 알아야 할 것과 나중에 공부해도 될 것 구분하기

## AI 서비스의 전체 그림

사용자가 웹사이트에 질문 입력 → 웹서버가 AI API에 요청 → 모델이 입력을 토큰으로 처리 → 앞의 맥락을 참고하며 다음 토큰을 차례로 예측 → 서버가 결과를 사용자에게 표시

여기서 꼭 기억할 게 있어요. **모델 내부를 설계하는 일과, 모델을 연결해 *쓸 만한 서비스*를 만드는 일은 서로 달라요.** 우리는 두 번째에 집중하면 되는데, 첫 번째의 핵심 원리를 조금 알아 두면 비용·속도·품질을 판단할 때 훨씬 수월해져요.

## 1. 토큰(Token): AI가 글을 읽는 단위

AI는 입력한 문장을 통째로 다루지 않아요. 모델이 정한 규칙에 따라 **토큰**이라는 조각으로 잘라서 처리하죠. 토큰은 글자 하나와 딱 맞아떨어지지 않아요. 단어 전체일 때도 있고, 단어 일부나 기호일 때도 있어요.

**예시:** 사주 서비스에서 사용자가 "올해 이직해도 될까요?"라고 물어봤다고 해 볼게요. 서버가 함께 보낸 지침, 사용자 질문, 모델이 만든 답변이 전부 토큰 수에 들어가요.

**서비스에서는 왜 중요할까요?** 대부분의 API는 요금과 입력 길이 제한을 토큰 단위로 정하거든요. 프롬프트가 길고, 대화 기록이 길고, 답변이 길수록 비용도 늘고 응답도 느려질 수 있어요.

**내가 알아야 할 수준**
- 토큰의 의미, 입력·출력 토큰과 가격 구조, 컨텍스트 길이 → 지금 알기
- 토크나이저 알고리즘 직접 구현 → 나중에

## 2. Transformer: AI가 문맥을 연결해 보는 기본 구조

예전 방식은 문장을 앞에서부터 순서대로 처리했는데, Transformer는 **Attention(어텐션)**으로 문장 속 여러 부분의 관계를 한꺼번에 계산해요. 지금의 대형 언어 모델은 대부분 이 구조를 바탕으로 발전했어요.

**예시:** "민지는 영희에게 책을 빌려줬다. 그녀는 다음 날 책을 돌려받았다." 여기서 '그녀'가 누구인지 알려면 주변 단어와의 관계를 봐야 하잖아요. Attention은 이런 연결을 학습하는 계산 방식이에요. (물론 문장 자체가 모호하면 모델도 확신하기 어려워요.)

**서비스에서는 왜 중요할까요?** 모델이 앞뒤 맥락을 참고하긴 하지만, 그렇다고 늘 정확한 사실을 아는 건 아니에요. 설명이 부족하거나 모호하면 엉뚱하게 연결할 수 있어요.

**내가 알아야 할 수준**
- 모델이 문맥의 관계를 계산한다는 것, 맥락을 잘 주는 게 중요하다는 것 → 지금 알기
- Attention 행렬 계산식과 차원 → 심화

## 3. Attention: 모든 단어를 똑같이 중요하게 보지 않아요

모델이 한 부분을 처리할 때, 다른 부분들과 얼마나 관련 있는지 계산해서 정보를 섞는 방식이에요. 단어마다 주의를 기울이는 정도가 다르죠.

**예시:** "사용자에게 저장 버튼이 보이지 않아요. 어디를 바꿔야 하나요?"라는 질문에서는 '저장 버튼', '보이지 않아요' 같은 표현이 문제 해결의 핵심이 될 수 있어요.

다만 하나 조심할 점이 있어요. Attention 가중치가 높다고 해서 그게 곧 모델의 '진짜 판단 이유'를 다 설명해 주는 건 아니에요.

**내가 알아야 할 수준**
- 핵심 원리만 이해 → 지금 알기
- Q·K·V 수식 → 모델 구조를 직접 공부할 때

## 4. KV Cache: 긴 답변에서 이전 계산을 재활용하는 메모

모델은 답변을 **한 토큰씩** 만들어요. 이때 앞에서 계산한 Key·Value 값을 저장해 두고 다음 토큰을 만들 때 다시 써요. 같은 계산을 매번 처음부터 반복하지 않게 돕는 장치예요.

**예시:** 한 번의 요청에서 긴 답변을 만들 때, 앞에서 처리한 토큰 정보를 재사용할 수 있어요. 그런데 **다른 API 요청이나 다른 대화로 넘어가도 KV Cache가 계속 유지된다는 뜻은 아니에요.** 제공업체의 캐싱 정책이나 '프롬프트 캐싱' 기능과는 구분해야 해요.

**서비스에서는 왜 중요할까요?** 모델을 직접 운영한다면 메모리 사용량과 동시 처리 수에 바로 영향을 줘요. 외부 API를 쓰는 입장이라면 캐시 내부 구조보다 가격, 응답 지연, 제공업체의 캐싱 정책을 확인하는 게 더 실용적이고요.

**내가 알아야 할 수준**
- 긴 입력·출력이 자원과 비용을 더 쓴다는 것 → 지금 알기
- GPU 메모리 계산식 → 직접 호스팅할 때

## 5. MoE(Mixture of Experts): 매번 모델 전체를 쓰지는 않는 구조

어떤 모델은 여러 **전문가 네트워크(Expert)**와, 어느 전문가를 쓸지 고르는 **라우터(Router)**로 이루어져 있어요. 토큰마다 일부 전문가만 골라서 계산하는 거죠.

**비유:** 큰 팀에서 모든 직원이 모든 문의를 처리하는 대신, 문의 성격에 맞는 담당자 몇 명만 일하는 것과 비슷해요. 다만 실제 전문가 네트워크가 사람처럼 '법률 담당', '디자인 담당'으로 깔끔하게 나뉜다는 뜻은 아니에요.

**서비스에서는 왜 중요할까요?** 모델 전체 파라미터 수와, 토큰마다 실제로 계산에 쓰는 파라미터 수가 다를 수 있거든요. 그렇다고 모델을 저장하고 운영하는 데 필요한 메모리까지 자동으로 줄어드는 건 아니에요.

**내가 알아야 할 수준**
- '큰 모델 = 매번 모든 계산을 다 하는 모델'은 아니라는 것 → 지금 알기
- 라우팅 알고리즘, 전문가 병렬화 → 심화

## 6. 모델을 만드는 사람과 연결해 쓰는 사람은 공부할 게 달라요

| 질문 | AI API로 웹서비스를 만드는 사람 | AI 모델을 직접 운영하는 사람 |
|---|---|---|
| 토큰 | 비용·입력 제한 확인 | 토크나이저·처리량 분석 |
| Transformer·Attention | 문맥 제공과 한계 이해 | 모델 구조·연산 최적화 |
| KV Cache | 응답 속도·제공업체 캐싱 정책 확인 | GPU 메모리·동시성 최적화 |
| MoE | 모델의 특성과 비용 비교 | 전문가 배치·통신 병목 관리 |
| 프롬프트 설계 | **우선적으로 학습** | 우선적으로 학습 |
| 평가·테스트 | **우선적으로 학습** | 우선적으로 학습 |

## 7. 찐망고 사주풀이로 생각해 보기

이 서비스의 AI 답변 품질이 떨어진다고 해 볼게요. 이럴 때는 Transformer 수식을 공부하는 것보다 아래 질문을 먼저 던져 보는 게 훨씬 도움이 돼요.

1. **입력:** 생년월일, 명식, 사용자 질문이 정확히 전달됐나?
2. **지침:** 설명 기준과 하면 안 되는 추측을 분명하게 알려 줬나?
3. **출력:** 답변 구조, 길이, 쉬운 문장 같은 원하는 형식을 정해 뒀나?
4. **검증:** 같은 유형의 사례를 반복 테스트하고 오류 유형을 모았나?
5. **운영:** 답변 길이, 비용, 오류, 응답 시간을 측정하고 있나?

이 다섯 가지는 모델 내부를 하나도 건드리지 않고 다룰 수 있어요. 결국 **AI 서비스 품질은 모델 성능만이 아니라 입력 데이터·지침·검증·UI가 함께 만드는 거예요.**

## 8. 수업에 적용한다면

**15분 활동: "AI 답변이 틀렸을 때 무엇을 고칠까?"**

- 사례: 로그인 화면을 만들어 달라고 했는데 버튼 색상·폰트·레이아웃이 시안과 다르게 나옴
- 학생이 원인을 세 가지로 분류하기: **정보 부족 / 지침 불명확 / 결과 검수 부족**
- 프롬프트·참고 이미지 설명·검수 체크리스트 중 무엇을 바꿀지 정하기
- 핵심: AI 내부 수식보다 **설계와 검증 능력**이 먼저 필요하다는 걸 체감하기

## 9. 스스로 확인하기

- 토큰이 많아지면 서비스 비용에 어떤 영향을 줄까?
- KV Cache와 API 업체의 프롬프트 캐싱은 왜 같은 말이 아닐까?
- AI 결과가 기대와 다를 때, 모델이 잘못됐다고 바로 결론 내려도 될까?
