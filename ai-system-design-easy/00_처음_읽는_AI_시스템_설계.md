# 처음 읽는 AI 시스템 설계

> 비개발자·웹 기획자·디자이너·AI 활용 개발자를 위한 입문서 01  
> 기반 주제: [AI System Design Guide — LLM Internals](https://github.com/ombharatiya/ai-system-design-guide)  
> 이 문서는 원문의 직역본이 아닌 **독립적인 초보자 해설**입니다. 모델별 최신 수치보다 원리와 서비스 설계 판단에 집중합니다.

## 이 장을 읽고 나면

- AI가 질문을 읽고 답변을 만들어 내는 기본 흐름을 설명할 수 있다.
- Transformer, 토큰, Attention, KV Cache, MoE가 왜 등장했는지 이해할 수 있다.
- API를 사용하는 서비스 개발자가 무엇을 알아야 하고, 무엇은 나중에 공부해도 되는지 구분할 수 있다.

## 먼저, AI 서비스의 전체 그림

사용자가 웹사이트에 질문 입력 → 웹서버가 AI API에 요청 → 모델이 입력을 토큰으로 처리 → 앞서 나온 맥락을 참고하면서 다음 토큰을 차례로 예측 → 서버가 결과를 사용자에게 표시.

**중요:** 모델 내부를 설계하는 일과, 모델을 연결해 *쓸 만한 서비스*를 만드는 일은 다르다. 서비스 개발자는 두 번째에 집중하되 첫 번째의 핵심 원리를 알면 비용·속도·품질을 판단하기 쉬워진다.

## 1. 토큰(Token): AI가 글을 읽는 단위

AI는 입력 문장을 그대로 한 덩어리로 다루지 않고, 모델이 정한 규칙에 따라 **토큰**이라는 조각으로 나눈다. 토큰은 글자 하나와 항상 일치하지 않는다. 단어 전체일 수도 있고 단어 일부, 기호일 수도 있다.

**예시:** 사주 서비스를 이용하는 사용자가 “올해 이직해도 될까요?”라고 질문한다. 서버가 전달한 지침, 사용자 입력, 모델이 생성한 답변 모두 토큰 수와 관련이 있다.

**서비스에서 왜 중요할까?** 많은 API의 요금과 입력 길이 제한이 토큰 단위로 정해진다. 긴 프롬프트·긴 대화 기록·긴 답변은 비용과 지연시간을 늘릴 수 있다.

**내가 알아야 할 수준:** 토큰의 의미, 입력·출력 토큰과 가격 구조, 컨텍스트 길이. *토크나이저 알고리즘을 직접 구현하는 방법은 나중에.*

## 2. Transformer: AI가 문맥을 연결해 보는 기본 구조

예전 순차 처리 방식과 달리 Transformer는 **Attention(어텐션)**을 이용해 문장 속 여러 부분의 관계를 계산한다. 대형 언어 모델은 대체로 이런 구조를 바탕으로 발전했다.

**예시:** “민지는 영희에게 책을 빌려줬다. 그녀는 다음 날 책을 돌려받았다.”라는 문장이 있다고 하자. '그녀'가 누구인지 판단하려면 주변 단어와 관계를 살펴야 한다. Attention은 이런 연결을 학습하는 계산 메커니즘이다. (문장 자체가 모호할 때는 모델도 확정하기 어렵다.)

**서비스에서 왜 중요할까?** 모델은 앞뒤 맥락을 참고하지만, 그렇다고 언제나 정확한 사실을 아는 것은 아니다. 설명이 불충분하거나 모호하면 잘못된 연결을 만들 수 있다.

**내가 알아야 할 수준:** 모델이 문맥의 관계를 계산한다는 사실과, 맥락 제공의 중요성. *Attention 행렬 계산식과 차원은 심화 학습용.*

## 3. Attention: 모든 단어를 똑같이 중요하게 보지 않는다

모델이 한 부분을 처리할 때 다른 부분들과 얼마나 관련이 있는지 계산해 정보를 섞는 방식이다. 각 부분에 주의를 주는 정도가 같지 않다.

**예시:** “사용자에게 저장 버튼이 보이지 않아요. 어디를 바꿔야 하나요?”라는 질문에서 '저장 버튼', '보이지 않아요' 같은 표현이 문제 해결에 핵심이 될 수 있다.

**주의:** Attention 가중치가 높다고 해서 그것만으로 모델의 '진짜 판단 이유'가 완전히 설명되는 것은 아니다.

**내가 알아야 할 수준:** 핵심 원리만 이해하면 충분하다. *Q·K·V 수식은 모델 구조를 직접 공부할 때.*

## 4. KV Cache: 긴 대화에서 이전 계산을 재활용하는 메모

모델이 답변을 **한 토큰씩 생성**할 때, 이전 위치의 Key·Value 계산 결과를 저장해 다음 토큰 생성에 재사용한다. 같은 내용을 매번 처음부터 다시 계산하지 않도록 돕는 장치다.

**예시:** 한 번의 요청에서 긴 답변을 생성할 때 앞에서 처리한 토큰의 정보를 재사용할 수 있다. **다른 API 요청이나 대화 사이에 KV Cache가 반드시 유지된다는 뜻은 아니다.** 제공업체의 캐싱 정책과 프롬프트 캐싱 기능은 구분해야 한다.

**서비스에서 왜 중요할까?** 모델을 직접 운영하면 메모리 사용량과 동시 처리 수에 직접 영향을 준다. 외부 API 이용자는 캐시 내부 구현보다 가격, 요청 지연, 제공업체의 캐싱 정책을 확인하는 편이 실용적이다.

**내가 알아야 할 수준:** 긴 입력·출력과 자원 비용의 관계. *GPU 메모리 계산식은 자체 호스팅 단계에서.*

## 5. MoE(Mixture of Experts): 매번 전체 모델을 쓰지는 않는 구조

일부 모델은 여러 **전문가 네트워크(Expert)**와 어떤 전문가를 사용할지 고르는 **라우터(Router)**를 사용한다. 입력 토큰마다 일부 전문가만 활성화해 계산을 수행할 수 있다.

**비유:** 큰 팀의 직원 모두가 모든 문의를 처리하는 대신, 문의 성격에 따라 필요한 담당자 몇 명이 일하는 것과 비슷하다. 다만 실제 전문가 네트워크가 사람처럼 '법률 담당', '디자인 담당'으로 명확하게 구분된다는 뜻은 아니다.

**서비스에서 왜 중요할까?** 모델이 가진 전체 파라미터 수와 토큰마다 계산에 사용하는 파라미터 수가 달라질 수 있다. 그렇다고 모델을 저장·운영하는 데 필요한 메모리까지 자동으로 작아지는 것은 아니다.

**내가 알아야 할 수준:** '큰 모델 = 매번 모든 계산을 다 하는 모델'은 아니라는 것. *라우팅 알고리즘·전문가 병렬화는 심화.*

## 6. 모델을 직접 만드는 사람과 연결해 쓰는 사람의 공부는 다르다

| 질문 | AI API로 웹서비스를 만드는 사람 | AI 모델을 직접 운영하는 사람 |
|---|---|---|
| 토큰 | 비용·입력 제한 확인 | 토크나이저·처리량 분석 |
| Transformer·Attention | 문맥 제공과 한계 이해 | 모델 구조·연산 최적화 |
| KV Cache | 응답 속도·제공업체 캐싱 정책 확인 | GPU 메모리·동시성 최적화 |
| MoE | 모델의 특성과 비용 비교 | 전문가 배치·통신 병목 관리 |
| 프롬프트 설계 | **우선적으로 학습** | 우선적으로 학습 |
| 평가·테스트 | **우선적으로 학습** | 우선적으로 학습 |

## 7. 찐망고 사주풀이를 예로 생각해 보기

이 서비스의 AI 응답 품질이 떨어진다고 해 보자. Transformer 수식을 공부하는 것보다 다음 질문이 우선이다.

1. **입력:** 생년월일, 명식, 사용자 질문이 정확히 전달되었나?
2. **지침:** 모델에게 설명의 기준과 금지할 추측을 분명하게 줬나?
3. **출력:** 답변 구조, 길이, 쉬운 문장 등 원하는 형식이 정의되어 있나?
4. **검증:** 동일한 유형의 사례를 반복 테스트하고 오류 유형을 모았나?
5. **운영:** 답변 길이, 비용, 오류, 응답 시간을 측정하나?

이 다섯 가지는 모델 내부 구조를 수정하지 않고도 다룰 수 있다. **AI 서비스 품질은 모델 성능뿐 아니라 입력 데이터·지침·검증·UI의 영향을 함께 받는다.**

## 8. 수업에 적용한다면

**15분 활동: “AI 답변이 틀렸을 때 무엇을 고칠까?”**

- 사례: 로그인 화면 생성 요청을 했는데 버튼 색상·폰트·레이아웃이 시안과 다르게 나왔다.
- 학생에게 원인을 세 범주로 분류하게 한다: **정보 부족 / 지침 불명확 / 결과 검수 부족**.
- 그다음 프롬프트·참고 이미지 설명·검수 체크리스트 중 무엇을 바꿀지 정하게 한다.
- 핵심: AI 내부 수식보다 **설계와 검증 능력**이 먼저 필요한 상황을 이해한다.

## 9. 스스로 확인하기

- 토큰이 많아지면 서비스 비용에 어떤 영향을 줄 수 있을까?
- KV Cache와 API 업체의 프롬프트 캐싱은 왜 같은 말이 아닐까?
- AI 결과가 기대와 다를 때 모델 자체가 잘못되었다고 바로 결론 내려도 될까?
