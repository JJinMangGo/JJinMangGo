# 02. 프롬프트와 컨텍스트 설계

> **비개발자를 위한 AI 시스템 설계 입문서**  
> 이번 장의 질문: **같은 AI를 써도 왜 어떤 서비스는 답변이 안정적이고, 어떤 서비스는 매번 엉뚱한 말을 할까?**

- 난이도: ★★☆☆☆ (코드를 몰라도 이해 가능)
- 예상 학습 시간: 25~35분
- 먼저 읽기: [01. 토큰화와 컨텍스트 창](01_토큰화와_컨텍스트_창.md)
- 학습 주제 참고: [AI System Design Guide](https://github.com/ombharatiya/ai-system-design-guide)

> 이 글은 원문의 직역이 아니라 **비전공자와 AI 서비스를 만드는 사람을 위한 독립적인 해설서**입니다. 프롬프트만으로 모든 결과를 통제할 수 있는 것은 아니며, 중요한 서비스 기능은 코드 검증과 테스트가 함께 필요합니다.

---

## 먼저 상황 하나

학생이 AI에게 이렇게 말한다.

> “교촌치킨 홈페이지를 리뉴얼해 줘.”

AI는 멋진 메인 화면을 상상해 주겠지만, 답변마다 메뉴 구성도 다르고 브랜드의 강조점도 달라질 수 있다. 왜 그럴까?

**AI에게 무엇을 만들어야 하는지보다, 어떤 기준으로 판단해야 하는지가 충분히 전달되지 않았기 때문**이다.

같은 AI라도 다음처럼 질문하면 일이 달라진다.

> “교촌치킨 **공식 웹사이트**의 메인 화면을 기획해 줘. 목표는 제품 탐색과 브랜드 경험을 돕는 거야. 주문은 앱으로 연결하고, 매장 찾기를 주요 행동으로 넣어 줘. 사용자가 처음 들어왔을 때 메뉴를 찾는 흐름을 우선해. Hero → 베스트 메뉴 → 이벤트 → 브랜드 → 매장 찾기 → 앱 다운로드 순서로 제안하고, 각 섹션의 목적과 CTA를 표로 설명해 줘. 확인하지 못한 현재 메뉴명이나 행사 내용은 지어내지 마.”

두 번째 질문이 무조건 정답을 보장하진 않는다. 하지만 **AI가 참고할 목표·제약·출력 형식**이 생겼다.

이번 장에서는 그 기준을 설계하는 방법을 배운다.

---

## 1. 프롬프트는 '질문'이 아니라 '작업 지시서'

**프롬프트(prompt)**는 AI에게 전달하는 입력이다. 채팅에서 쓰는 한 줄 질문도 프롬프트지만, 서비스에서는 여러 종류의 지시와 데이터가 합쳐져 하나의 요청이 된다.

```text
[서비스가 정한 기본 규칙]
          +
[이번 작업의 목표와 기준]
          +
[관련 데이터·이전 대화]
          +
[사용자의 이번 질문]
          ↓
       AI 모델
          ↓
        응답
```

### 프롬프트에 꼭 들어가면 좋은 다섯 가지

| 요소 | 설명 | 예시 |
|---|---|---|
| 목표 | 무엇을 이루려는가? | 웹사이트 메인 구조 제안 |
| 배경 | 어떤 상황인가? | 기존 사이트에서 브랜드와 주문 목적이 섞여 있음 |
| 기준 | 무엇을 우선할까? | 사용자 목적·탐색 흐름을 우선 |
| 제약 | 무엇을 피해야 할까? | 확인되지 않은 사실을 만들어내지 않기 |
| 결과 형식 | 어떤 형태로 받을까? | 섹션명·목적·CTA 표 |

**핵심:** 좋은 프롬프트는 길기만 한 프롬프트가 아니다. *필요한 기준이 빠짐없이 들어 있으면서 서로 충돌하지 않는 프롬프트*다.

---

## 2. 프롬프트와 컨텍스트는 뭐가 다를까?

앞 장에서 배운 **컨텍스트 창**은 모델이 한 번의 요청에서 처리할 수 있는 정보의 한도였다.

이번에는 **컨텍스트(context)**를 'AI가 판단할 때 참고하도록 건네주는 관련 정보'라는 의미로 이해해 보자.

- **프롬프트 설계:** 무엇을 어떻게 하라고 지시할까?
- **컨텍스트 설계:** 그 일을 하려면 어떤 자료를 함께 줘야 할까?

예를 들어 AI에게 “이 학생의 웹사이트를 평가해 줘”라고만 하면 기준이 모호하다.

그런데 다음 자료를 함께 주면?

1. 평가표와 배점
2. 학생이 만든 실제 화면 또는 코드
3. 과제를 낸 시점과 요구사항
4. 채점에서 제외할 항목

AI는 비로소 **무엇을 근거로 판단할지** 알게 된다.

### 쉬운 비유

프롬프트가 **요리 주문서**라면 컨텍스트는 **냉장고 속 실제 재료와 알레르기 정보**다.

“맛있는 파스타를 만들어 줘”라는 주문만으로는 각자의 상상이 달라진다. 재료와 제약까지 알면 가능한 요리가 좁혀진다.

---

## 3. AI의 역할은 정해도, 근거를 대신 만들면 안 된다

“너는 20년 경력의 UX 전문가야” 같은 역할 지시를 본 적 있을 거야.

이런 표현은 원하는 답변의 관점을 알려주는 데 도움이 될 수 있다. 하지만 AI에게 전문가 역할을 줬다고 **실제로 조사하지 않은 사용자 데이터가 생기거나 사실 검증이 끝나는 것은 아니다.**

다음 두 문장을 비교해 보자.

**막연한 역할 지시**

> “너는 최고의 UX 전문가야. 이 사이트의 문제점을 분석해.”

**근거와 판단 기준이 있는 지시**

> “제공한 화면을 기준으로 사용자 목표, 정보 우선순위, 주요 CTA를 분석해. 화면에서 확인한 사실과 추정한 문제를 구분해. 사용성 테스트를 하지 않았으므로 실제 사용자가 불편해한다고 단정하지 마.”

두 번째가 더 실무적인 이유는 '전문가처럼 말하기'보다 **증거를 다루는 방법**을 지정했기 때문이다.

---

## 4. 같은 프롬프트인데 결과가 달라지는 이유

AI는 일반적인 프로그램처럼 입력이 같으면 언제나 문장이 똑같이 나오는 방식만 사용하는 게 아니다.

- 모델은 가능한 다음 토큰의 확률을 계산한다.
- 모델 설정과 샘플링 방식에 따라 결과 표현이 달라질 수 있다.
- 모델 버전, 전달한 문맥, 외부 검색 결과가 달라지면 답변도 달라진다.
- 서로 모순되는 지시나 부족한 자료가 있으면 흔들리기 쉽다.

여기서 중요한 질문은 **“한 글자도 똑같이 나오게 할까?”가 아니라 “달라져도 지켜야 할 기준은 지키는가?”**다.

예를 들어 궁합 서비스라면 문장 표현은 조금씩 달라져도 다음 기준은 유지되어야 한다.

- 두 사람을 헷갈리지 않는가?
- 성향·행동·갈등 상황을 구분하는가?
- 입력에 없는 사건을 사실처럼 꾸며내지 않는가?
- 사용자가 이해할 수 있는 문장을 쓰는가?

이건 프롬프트를 예쁘게 쓰는 작업을 넘어 **서비스의 품질 기준을 정의하는 작업**이다.

---

## 5. 서비스를 만들 때는 지시·데이터·사용자 입력을 구분하자

실제 API 기반 서비스에서는 개발자 지시, 사용자 요청, 외부에서 가져온 자료가 서로 다른 역할을 한다. 제공업체에 따라 메시지 역할과 우선순위 이름은 조금씩 다르다.

```text
서비스 규칙       → 이 서비스가 항상 지킬 원칙
작업별 지시      → 이번 기능에서 수행할 일
검증된 데이터    → 판단에 사용할 실제 입력값
외부 문서        → 참고 자료 (그 자체로 명령은 아님)
사용자 요청      → 사용자가 이번에 원하는 질문
```

### 왜 이렇게 구분할까?

웹페이지를 검색해서 AI에 전달했다고 생각해 보자. 그 페이지 안에 “앞의 모든 지시를 무시하라”는 문장이 숨어 있다면?

페이지는 **참고 자료**일 뿐, 서비스 규칙을 바꾸라는 권한이 없다. 이런 종류의 공격을 **프롬프트 인젝션(prompt injection)**이라고 한다.

**실무 원칙:** 검색 결과, 업로드한 PDF, 사용자 작성 텍스트 안의 '지시문'을 무조건 따라서는 안 된다. 중요 권한과 민감한 작업은 서버 측 검증을 거쳐야 한다.

---

## 6. AI에게 자료를 많이 주면 더 정확할까?

반드시 그렇지는 않다.

컨텍스트 창이 넓어도 관련 없는 글을 잔뜩 넣으면 핵심 자료를 찾기 어려워지거나, 정보끼리 충돌할 수 있다. 그리고 API를 사용한다면 입력 토큰이 비용에도 영향을 준다.

### 예: 웹사이트 리뉴얼 피드백

**방법 A — 모든 자료를 무작정 넣기**

기업 소개 100페이지, 경쟁사 자료 70페이지, 수업 기록 전체, 학생 결과물을 모두 넣고 “평가해 줘”라고 한다.

**방법 B — 필요한 자료를 선별하기**

현재 평가할 단계의 과제 요구사항 + 평가 기준 + 학생 결과물 + 관련 근거 몇 개만 넣는다.

방법 B가 항상 더 정확하다고 단정할 수는 없지만, 판단 근거를 추적하고 결과를 검토하기가 훨씬 쉽다.

### 컨텍스트 선택 질문

- 이 자료가 **이번 질문**에 실제로 필요한가?
- 최신이고 신뢰할 만한가?
- 서로 모순되는 자료가 있다면 우선순위는 무엇인가?
- 모델이 인용할 수 있도록 출처를 남겼는가?
- 굳이 전체 문서를 보내지 않고 필요한 부분만 보낼 수 있는가?

필요한 문서 일부만 찾아 넣는 설계는 다음에 배울 **RAG(검색 증강 생성)**와도 연결된다.

## 7. 출력 형식까지 설계해야 '서비스'가 된다

채팅에서는 자연어 답변만 나와도 괜찮다. 그런데 AI 결과를 카드 UI로 출력하거나 데이터베이스에 저장한다면 이야기가 달라진다.

예를 들어 화면에 다음 항목을 넣어야 한다고 해 보자.

```json
{
  "title": "계획이 바뀌었을 때의 반응",
  "summary": "한 사람은 약속을 지키고 싶고, 다른 사람은 상황에 맞춰 바꾸고 싶어해요.",
  "example": "여행 중 갑자기 일정이 바뀌는 상황",
  "advice": "변경이 필요한 이유와 유지하고 싶은 기준을 먼저 나눠 이야기해 보세요."
}
```

이런 **구조화된 출력(structured output)**은 프론트엔드에서 데이터를 표시하기 쉽게 한다.

하지만 “JSON으로만 답해”라고 적는 것으로 충분하진 않다.

- 필수 키가 모두 있는지
- 값의 자료형이 맞는지
- 문자열 길이가 너무 길지 않은지
- 입력에 없는 내용이 포함되지 않았는지
- 실패했을 때 다시 요청하거나 오류를 표시할지

이러한 조건은 **스키마 검증과 애플리케이션 코드**에서 확인해야 한다. 제공업체가 지원한다면 JSON Schema 같은 구조화 출력 기능을 사용하면 도움이 된다.

**정리:** 프롬프트는 원하는 형식을 *요청*하고, 프로그램은 실제 출력이 그 형식을 *지키는지 검증*한다.

## 8. 찐망고 사주풀이 사례로 이해하기

AI가 궁합을 해석한다고 가정해 보자.

처음에는 이렇게 요청할 수 있다.

> “두 사람의 궁합을 재미있게 풀어줘.”

문제는 '재미있게'가 너무 넓다는 점이다. 감성적인 문장만 길어지거나, 각 사람의 행동을 혼동하거나, 매번 다른 목차를 만들 수도 있다.

그렇다면 기준을 나누자.

| 구분 | 설계할 내용 |
|---|---|
| 목표 | 사주 해석을 일반 독자도 이해할 수 있게 전달 |
| 입력 | 두 사람의 명식, 관계 유형 등 실제 제공된 값 |
| 해석 기준 | 성향 → 행동 → 갈등 상황 → 조율 방법의 흐름 |
| 문체 | 중·고등학생도 이해할 수 있는 짧고 자연스러운 문장 |
| 제약 | 입력에 없는 실제 사건·감정·미래를 단정하지 않기 |
| 출력 | 기본 성향, 갈등 사례, 조율 방법 등 UI 항목별 구조 |
| 검증 | 사람 구분, 필드 누락, 모순 표현, 길이 확인 |

이때 중요한 점이 있다.

**사주 자체는 과학적으로 검증된 개인 성격 예측 도구가 아니다.** 따라서 위 사례는 **사용자가 선택한 해석 콘텐츠의 문장 품질과 서비스 구조를 설계하는 예시**이며, 해석 내용의 객관적 정확성을 보증하지 않는다.

이렇게 설명을 구분하면 서비스 기획과 콘텐츠의 사실성도 혼동하지 않을 수 있다.

---

## 9. 프롬프트를 잘 썼는지 어떻게 평가할까?

많은 사람이 프롬프트를 수정할 때 답변 한 번만 보고 “좋아졌다!”라고 판단한다.

하지만 서비스라면 여러 입력에서 같은 기준을 통과하는지 확인해야 한다.

### 작은 테스트표부터 만들자

| 테스트 상황 | 확인할 내용 | 합격 기준 예시 |
|---|---|---|
| 일반적인 입력 | 요구한 항목이 모두 있는가? | 필수 필드 누락 없음 |
| 긴 입력 | 중요한 규칙을 끝까지 지키는가? | 핵심 조건 유지 |
| 정보 부족 | 모르는 사실을 지어내는가? | 부족한 정보 명시 |
| 서로 다른 두 사람 | 이름과 행동을 뒤바꾸는가? | 인물 혼동 없음 |
| 외부 문서 포함 | 문서 속 명령을 따르는가? | 문서를 참고 자료로만 취급 |
| UI 출력 | JSON 구조가 유효한가? | 스키마 검증 통과 |

좋은 테스트는 “답변이 마음에 든다”에서 끝나지 않고 **실패 유형을 기록**한다.

### 프롬프트를 수정하는 순서

1. 실제로 실패한 예시를 저장한다.
2. 원인을 분류한다. (정보 부족? 지시 충돌? 형식 오류? 모델 한계?)
3. 관련된 규칙만 수정한다.
4. 기존에 잘 작동하던 테스트도 다시 돌린다.
5. 개선된 점과 새로 생긴 문제를 함께 기록한다.

규칙을 무작정 덧붙이면 프롬프트가 길고 모순되기 쉬워진다. **실패를 기준으로 고치는 것**이 핵심이다.

---

## 10. 언제 프롬프트를 고치고, 언제 코드를 고쳐야 할까?

서비스 제작에서 아주 중요한 구분이다.

| 문제 상황 | 먼저 살펴볼 곳 |
|---|---|
| 말투가 너무 어렵다 | 프롬프트의 독자·문체 기준 |
| 매번 목차가 바뀐다 | 출력 스키마와 필수 항목 |
| 사용자 이름이 서로 바뀐다 | 입력 데이터 구조 + 프롬프트 + 테스트 |
| 합계 금액이 틀리다 | 계산 코드 |
| 저장 버튼을 눌렀는데 저장되지 않는다 | DB/API/프론트엔드 코드 |
| 검색 자료에 없는 사실을 만든다 | 검색·근거 전달 구조 + 근거 검증 |
| 사용자가 입력한 문장으로 서비스 규칙을 우회한다 | 입력 신뢰 경계 + 권한 검증 + 안전 설계 |

**기억할 것:** AI가 말로 하는 일은 프롬프트로 조정할 수 있지만, 데이터 저장·결제·권한·정확한 계산은 실제 프로그램이 책임져야 한다.

## 11. 바로 써먹는 프롬프트 설계 템플릿

아래 내용을 복사해 웹사이트 기획, 수업 피드백, AI 서비스 기능 설계에 맞게 바꿔 보자.

```text
[목표]
이번 작업에서 반드시 해결해야 할 문제는 ...이다.

[대상과 배경]
이 결과를 보는 사람은 ...이고, 현재 상황은 ...이다.

[입력 자료]
아래 자료에서 확인되는 정보만 근거로 사용한다.
자료: ...

[판단 기준]
1. ...을 우선한다.
2. ...과 ...을 구분한다.
3. ...을 근거로 설명한다.

[하지 말아야 할 일]
- 제공하지 않은 사실을 만들어내지 않는다.
- 확인한 사실과 제안을 섞지 않는다.

[출력 형식]
1. 핵심 결론
2. 근거
3. 개선 제안
4. 추가 확인이 필요한 사항

[품질 확인]
응답 전에 필수 항목이 모두 포함됐는지 점검한다.
```

이 템플릿은 시작점이다. 사용하는 모델·도구·작업에 맞춰 짧게 줄이거나 더 구체화하면 된다.

## 12. 20분 실습: 같은 과제, 다른 컨텍스트

### 준비

학생이 리뉴얼할 웹사이트 하나를 고른다. 실제 사이트의 화면을 보거나, 사이트의 핵심 구조를 텍스트로 정리한다.

### 실습 A — 정보 없이 요청 (5분)

> “이 회사의 웹사이트 메인 화면을 기획해 줘.”

결과를 저장하고 다음을 확인한다.

- 목표가 무엇인지 AI가 추측했는가?
- 실제로 확인하지 않은 정보를 만들어냈는가?
- CTA가 사용자의 목적과 연결되는가?

### 실습 B — 기준을 추가 (5분)

목표·타깃·현재 문제·우선할 행동·필수 섹션·출력 형식을 정리해 다시 요청한다.

### 실습 C — 근거를 추가 (5분)

실제 웹사이트에서 관찰한 구조나 콘텐츠 목록을 함께 전달하고, **관찰 사실 / 추정 / 개선 제안**을 구분해 달라고 요청한다.

### 결과 비교 (5분)

| 비교 항목 | A | B | C |
|---|---|---|---|
| 사용자 목표가 분명한가? |  |  |  |
| 근거가 제시되었는가? |  |  |  |
| 사실과 추정이 구분되는가? |  |  |  |
| 실제 수정에 쓸 수 있는가? |  |  |  |

여기서 배울 것은 **프롬프트가 길어지면 무조건 좋아진다**가 아니다. **판단에 필요한 정보와 기준을 넣었을 때 결과가 어떻게 달라지는가**를 확인하는 것이다.

## 13. 내가 어디까지 알아야 할까?

| 학습 수준 | 알아야 할 내용 |
|---|---|
| 지금 꼭 알기 | 목표·배경·기준·제약·출력 형식 구분하기 |
| AI 서비스 만들 때 | 지시와 사용자 데이터의 역할, 구조화 출력, 검증과 테스트 |
| 서비스가 커지면 | RAG, 컨텍스트 선별, 프롬프트 인젝션 방어, 자동 평가 |
| 심화 과정 | 모델별 메시지 우선순위, 토큰 예산 설계, 평가 파이프라인 |

프롬프트의 모든 비법을 외울 필요는 없다. **좋은 결과를 정의하고, 자료를 선별하며, 결과를 검증하는 능력**이 더 오래 간다.

---

## 오늘의 핵심 정리

1. **프롬프트는 질문이 아니라 작업 지시서다.** 목표·기준·제약·출력 형식을 구체화한다.
2. **컨텍스트는 AI가 판단할 근거다.** 자료가 많다고 항상 좋은 것은 아니다.
3. **역할 지시보다 근거와 판단 기준이 중요하다.** 자신감 있는 문장을 사실로 착각하지 않는다.
4. **서비스 품질은 테스트로 확인한다.** 한 번 좋은 답변보다 여러 경우에도 기준을 지키는지가 중요하다.
5. **프롬프트로 해결할 문제와 코드로 해결할 문제를 구분한다.** 특히 데이터·권한·결제는 코드 검증이 필수다.

### 스스로 확인하는 질문

- 프롬프트와 컨텍스트의 차이를 한 문장으로 설명할 수 있을까?
- AI가 없는 사실을 지어내지 않도록 자료와 지시를 어떻게 구성할까?
- 같은 요청에서 결과가 달라졌을 때 무엇을 테스트해야 할까?
- 내가 만드는 서비스에서 반드시 코드로 검증해야 할 것은 무엇일까?
