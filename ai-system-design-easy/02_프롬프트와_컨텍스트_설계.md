# 02. 프롬프트와 컨텍스트 설계

> **비개발자를 위한 AI 시스템 설계 입문서 · 02**  
> 이번 장의 질문: **같은 AI를 써도 왜 어떤 서비스는 답변이 안정적이고, 어떤 서비스는 매번 엉뚱한 말을 할까?**

- 난이도: ★★☆☆☆ — 코드를 몰라도 이해 가능
- 예상 학습 시간: 25~35분
- 먼저 읽기: [01. 토큰화와 컨텍스트 창](01_토큰화와_컨텍스트_창.md)
- 참고 원문: [AI System Design Guide — Prompt Engineering Fundamentals](https://github.com/ombharatiya/ai-system-design-guide/blob/main/05-prompting-and-context/01-prompt-engineering-fundamentals.md) · [Context Engineering](https://github.com/ombharatiya/ai-system-design-guide/blob/main/05-prompting-and-context/05-context-engineering.md)

> 이 글은 원문을 옮긴 번역본이 아니라, 원문의 핵심 개념을 초보자 눈높이에 맞춰 새로 풀어 쓴 **독립 해설**이에요. 프롬프트만으로 모든 결과를 통제할 수는 없어서, 중요한 기능은 코드 검증과 테스트가 꼭 함께 필요해요.

---

## 먼저 상황 하나

학생이 AI에게 이렇게 말해요.

> "교촌치킨 홈페이지를 리뉴얼해 줘."

AI는 그럴듯한 메인 화면을 상상해 주긴 하는데, 물어볼 때마다 메뉴 구성도 다르고 브랜드에서 강조하는 부분도 달라져요. 왜 그럴까요?

**무엇을 만들지는 말했지만, 어떤 기준으로 판단해야 하는지는 충분히 알려 주지 않았기 때문**이에요.

같은 AI라도 이렇게 물어보면 얘기가 달라져요.

> "교촌치킨 **공식 웹사이트**의 메인 화면을 기획해 줘. 목표는 제품 탐색과 브랜드 경험을 돕는 거야. 주문은 앱으로 연결하고, 매장 찾기를 주요 행동으로 넣어 줘. 사용자가 처음 들어왔을 때 메뉴를 찾는 흐름을 우선해. Hero → 베스트 메뉴 → 이벤트 → 브랜드 → 매장 찾기 → 앱 다운로드 순서로 제안하고, 각 섹션의 목적과 CTA를 표로 설명해 줘. 확인하지 못한 현재 메뉴명이나 행사 내용은 지어내지 마."

두 번째 질문이 정답을 보장해 주진 않아요. 그래도 **AI가 참고할 목표·제약·출력 형식**이 생겼죠.

이번 장에서는 바로 그 기준을 설계하는 방법을 알아볼게요.

---

## 1. 프롬프트는 '질문'이 아니라 '작업 지시서'

**프롬프트(prompt)**는 AI에게 건네는 입력이에요. 채팅창에 쓰는 한 줄 질문도 프롬프트지만, 서비스에서는 여러 지시와 데이터가 합쳐져서 하나의 요청이 돼요.

```text
[서비스가 정한 기본 규칙]
          +
[이번 작업의 목표와 기준]
          +
[관련 데이터·이전 대화]
          +
[사용자의 이번 질문]
          ↓
       AI 모델
          ↓
        응답
```

### 프롬프트에 들어가면 좋은 다섯 가지

| 요소 | 설명 | 예시 |
|---|---|---|
| 목표 | 무엇을 이루려는가? | 웹사이트 메인 구조 제안 |
| 배경 | 어떤 상황인가? | 기존 사이트에서 브랜드와 주문 목적이 섞여 있음 |
| 기준 | 무엇을 우선할까? | 사용자 목적·탐색 흐름을 우선 |
| 제약 | 무엇을 피해야 할까? | 확인되지 않은 사실을 만들어내지 않기 |
| 결과 형식 | 어떤 형태로 받을까? | 섹션명·목적·CTA 표 |

좋은 프롬프트는 그냥 긴 프롬프트가 아니에요. *필요한 기준이 빠짐없이 들어 있으면서 서로 부딪히지 않는 프롬프트*예요.

---

## 2. 프롬프트와 컨텍스트는 뭐가 다를까요?

앞 장에서 본 **컨텍스트 창**은 모델이 한 번에 처리할 수 있는 정보의 한도였죠.

이번에는 **컨텍스트(context)**를 'AI가 판단할 때 참고하라고 건네주는 관련 정보'로 이해해 볼게요.

- **프롬프트 설계:** 무엇을 어떻게 하라고 지시할까?
- **컨텍스트 설계:** 그 일을 하려면 어떤 자료를 같이 줘야 할까?

예를 들어 "이 학생의 웹사이트를 평가해 줘"라고만 하면 기준이 애매해요.

그런데 이런 자료를 같이 주면 어떨까요?

1. 평가표와 배점
2. 학생이 만든 실제 화면이나 코드
3. 과제를 낸 시점과 요구사항
4. 채점에서 빼야 할 항목

그제야 AI가 **무엇을 근거로 판단할지** 알게 돼요.

### 쉬운 비유

프롬프트가 **요리 주문서**라면, 컨텍스트는 **냉장고 속 실제 재료와 알레르기 정보**예요.

"맛있는 파스타 만들어 줘"라는 주문만으로는 사람마다 떠올리는 게 다르잖아요. 재료와 제약까지 알면 만들 수 있는 요리가 확 좁혀지죠.

---

## 3. AI에게 역할은 줘도, 근거를 대신 만들게 하면 안 돼요

"너는 20년 경력의 UX 전문가야" 같은 역할 지시, 한 번쯤 보셨을 거예요.

이런 표현은 원하는 관점을 알려 주는 데는 도움이 돼요. 그런데 AI에게 전문가 역할을 줬다고 해서 **조사하지도 않은 사용자 데이터가 생기거나, 사실 검증이 끝나는 건 아니에요.**

두 지시를 비교해 볼게요.

**막연한 역할 지시**

> "너는 최고의 UX 전문가야. 이 사이트의 문제점을 분석해."

**근거와 판단 기준이 있는 지시**

> "제공한 화면을 기준으로 사용자 목표, 정보 우선순위, 주요 CTA를 분석해. 화면에서 확인한 사실과 추정한 문제를 구분해. 사용성 테스트를 하지 않았으므로 실제 사용자가 불편해한다고 단정하지 마."

두 번째가 더 실무적인 이유는, '전문가처럼 말하기' 대신 **증거를 어떻게 다룰지**를 정해 줬기 때문이에요.

---

## 4. 같은 프롬프트인데 왜 결과가 달라질까요?

AI는 일반 프로그램처럼 '입력이 같으면 문장도 늘 똑같이' 나오는 방식으로만 움직이지 않아요.

- 모델은 다음에 올 토큰의 확률을 계산함
- 모델 설정과 샘플링 방식에 따라 표현이 달라질 수 있음
- 모델 버전, 함께 보낸 문맥, 외부 검색 결과가 바뀌면 답도 바뀜
- 지시가 서로 모순되거나 자료가 부족하면 쉽게 흔들림

그래서 중요한 질문은 **"한 글자도 똑같이 나오게 할 수 있을까?"가 아니라 "표현은 달라져도 지켜야 할 기준은 지키고 있나?"**예요.

예를 들어 궁합 서비스라면 문장은 조금씩 달라져도 이런 기준은 늘 지켜야겠죠.

- 두 사람을 헷갈리지 않는가?
- 성향·행동·갈등 상황을 구분하는가?
- 입력에 없는 사건을 사실처럼 꾸며내지 않는가?
- 사용자가 이해할 수 있는 문장인가?

이건 프롬프트를 예쁘게 다듬는 걸 넘어서 **서비스의 품질 기준을 정하는 일**이에요.

---

## 5. 서비스에서는 지시·데이터·사용자 입력을 나눠 주세요

실제 API 서비스에서는 개발자 지시, 사용자 요청, 외부에서 가져온 자료가 각자 다른 역할을 해요. 제공업체마다 메시지 역할 이름이나 우선순위는 조금씩 다르고요.

```text
서비스 규칙       → 이 서비스가 항상 지킬 원칙
작업별 지시      → 이번 기능에서 수행할 일
검증된 데이터    → 판단에 사용할 실제 입력값
외부 문서        → 참고 자료 (그 자체로 명령은 아님)
사용자 요청      → 사용자가 이번에 원하는 질문
```

### 왜 이렇게 나눠야 할까요?

웹페이지를 검색해서 AI에게 넘겼다고 해 볼게요. 그런데 그 페이지 안에 "앞의 모든 지시를 무시하라"는 문장이 숨어 있다면요?

그 페이지는 어디까지나 **참고 자료**일 뿐, 서비스 규칙을 바꿀 권한이 없어요. 이런 공격을 **프롬프트 인젝션(prompt injection)**이라고 해요.

**실무 원칙:** 검색 결과, 업로드한 PDF, 사용자가 쓴 텍스트 안에 들어 있는 '지시문'을 그대로 따르면 안 돼요. 중요한 권한이나 민감한 작업은 반드시 서버에서 한 번 더 검증해야 하고요.

---

## 6. 자료를 많이 주면 더 정확해질까요?

꼭 그렇지는 않아요.

컨텍스트 창이 넓어도 관련 없는 글을 잔뜩 넣으면 핵심 자료를 찾기 어려워지거나 정보끼리 충돌할 수 있어요. API를 쓴다면 입력 토큰이 늘어나서 비용도 올라가고요.

### 예: 웹사이트 리뉴얼 피드백

**방법 A — 자료를 몽땅 넣기**

기업 소개 100페이지, 경쟁사 자료 70페이지, 수업 기록 전체, 학생 결과물까지 다 넣고 "평가해 줘"라고 해요.

**방법 B — 필요한 자료만 고르기**

지금 평가할 단계의 과제 요구사항 + 평가 기준 + 학생 결과물 + 관련 근거 몇 개만 넣어요.

방법 B가 항상 더 정확하다고 단정할 순 없지만, 판단 근거를 따라가고 결과를 검토하기는 훨씬 쉬워요.

### 컨텍스트 고를 때 던질 질문

- 이 자료가 **이번 질문**에 정말 필요한가?
- 최신이고 믿을 만한가?
- 서로 모순되는 자료가 있다면 무엇을 우선할까?
- 모델이 인용할 수 있게 출처를 남겼나?
- 전체 문서 대신 필요한 부분만 보낼 수 있나?

필요한 문서 일부만 찾아서 넣는 설계는 다음 장의 **RAG(검색 증강 생성)**와 바로 연결돼요.

## 7. 출력 형식까지 설계해야 '서비스'가 돼요

채팅에서는 자연어 답변만 나와도 괜찮아요. 그런데 AI 결과를 카드 UI로 보여 주거나 데이터베이스에 저장해야 한다면 얘기가 달라지죠.

예를 들어 화면에 이런 항목이 들어가야 한다고 해 볼게요.

```json
{
  "title": "계획이 바뀌었을 때의 반응",
  "summary": "한 사람은 약속을 지키고 싶고, 다른 사람은 상황에 맞춰 바꾸고 싶어해요.",
  "example": "여행 중 갑자기 일정이 바뀌는 상황",
  "advice": "변경이 필요한 이유와 유지하고 싶은 기준을 먼저 나눠 이야기해 보세요."
}
```

이런 **구조화된 출력(structured output)**은 프론트엔드에서 데이터를 보여 주기 쉽게 해 줘요.

다만 "JSON으로만 답해"라고 적는 것만으로는 부족해요. 이런 것들은 따로 확인해야 하거든요.

- 필수 키가 다 있는지
- 값의 자료형이 맞는지
- 문자열이 너무 길지 않은지
- 입력에 없는 내용이 들어가지 않았는지
- 실패했을 때 다시 요청할지, 오류를 보여 줄지

이런 조건은 **스키마 검증과 애플리케이션 코드**에서 확인해야 해요. 제공업체가 지원한다면 JSON Schema 같은 구조화 출력 기능을 쓰면 도움이 되고요.

**정리하면:** 프롬프트는 원하는 형식을 *요청*하고, 프로그램은 실제 출력이 그 형식을 *지켰는지 검증*해요.

## 8. 찐망고 사주풀이로 이해하기

AI가 궁합을 해석한다고 해 볼게요.

처음엔 이렇게 요청할 수 있어요.

> "두 사람의 궁합을 재미있게 풀어줘."

문제는 '재미있게'가 너무 넓다는 거예요. 감성적인 문장만 길어지거나, 두 사람의 행동을 헷갈리거나, 매번 다른 목차를 만들 수도 있어요.

그럼 기준을 나눠 볼까요?

| 구분 | 설계할 내용 |
|---|---|
| 목표 | 사주 해석을 일반 독자도 이해할 수 있게 전달 |
| 입력 | 두 사람의 명식, 관계 유형 등 실제 제공된 값 |
| 해석 기준 | 성향 → 행동 → 갈등 상황 → 조율 방법의 흐름 |
| 문체 | 중·고등학생도 이해할 수 있는 짧고 자연스러운 문장 |
| 제약 | 입력에 없는 실제 사건·감정·미래를 단정하지 않기 |
| 출력 | 기본 성향, 갈등 사례, 조율 방법 등 UI 항목별 구조 |
| 검증 | 사람 구분, 필드 누락, 모순 표현, 길이 확인 |

여기서 꼭 짚고 갈 게 있어요.

**사주 자체는 과학적으로 검증된 성격 예측 도구가 아니에요.** 그래서 위 사례는 **사용자가 선택한 해석 콘텐츠의 문장 품질과 서비스 구조를 설계하는 예시**이고, 해석 내용이 객관적으로 맞는다고 보증하는 건 아니에요.

이렇게 나눠 두면 서비스 기획과 콘텐츠의 사실성을 헷갈리지 않을 수 있어요.

---

## 9. 프롬프트를 잘 썼는지 어떻게 알 수 있을까요?

프롬프트를 고친 다음 답변 한 번만 보고 "좋아졌다!" 하는 경우가 많아요.

그런데 서비스라면 여러 입력에서도 같은 기준을 통과하는지 확인해야 해요.

### 작은 테스트표부터 만들어 보세요

| 테스트 상황 | 확인할 내용 | 합격 기준 예시 |
|---|---|---|
| 일반적인 입력 | 요구한 항목이 모두 있는가? | 필수 필드 누락 없음 |
| 긴 입력 | 중요한 규칙을 끝까지 지키는가? | 핵심 조건 유지 |
| 정보 부족 | 모르는 사실을 지어내는가? | 부족한 정보 명시 |
| 서로 다른 두 사람 | 이름과 행동을 뒤바꾸는가? | 인물 혼동 없음 |
| 외부 문서 포함 | 문서 속 명령을 따르는가? | 문서를 참고 자료로만 취급 |
| UI 출력 | JSON 구조가 유효한가? | 스키마 검증 통과 |

좋은 테스트는 "답변이 마음에 든다"에서 끝나지 않고 **어떻게 실패했는지를 기록**해요.

### 프롬프트 고치는 순서

1. 실제로 실패한 예시 저장하기
2. 원인 분류하기 (정보 부족? 지시 충돌? 형식 오류? 모델 한계?)
3. 관련된 규칙만 고치기
4. 원래 잘되던 테스트도 다시 돌려 보기
5. 좋아진 점과 새로 생긴 문제 같이 기록하기

규칙을 계속 덧붙이기만 하면 프롬프트가 길어지고 모순도 생기기 쉬워요. **실패를 기준으로 고치기!** 이게 핵심이에요.

---

## 10. 프롬프트를 고칠까, 코드를 고칠까?

서비스를 만들 때 정말 중요한 구분이에요.

| 문제 상황 | 먼저 살펴볼 곳 |
|---|---|
| 말투가 너무 어렵다 | 프롬프트의 독자·문체 기준 |
| 매번 목차가 바뀐다 | 출력 스키마와 필수 항목 |
| 사용자 이름이 서로 바뀐다 | 입력 데이터 구조 + 프롬프트 + 테스트 |
| 합계 금액이 틀리다 | 계산 코드 |
| 저장 버튼을 눌렀는데 저장되지 않는다 | DB/API/프론트엔드 코드 |
| 검색 자료에 없는 사실을 만든다 | 검색·근거 전달 구조 + 근거 검증 |
| 사용자가 입력한 문장으로 서비스 규칙을 우회한다 | 입력 신뢰 경계 + 권한 검증 + 안전 설계 |

AI가 '말로 하는 일'은 프롬프트로 조정할 수 있어요. 하지만 데이터 저장·결제·권한·정확한 계산은 실제 프로그램이 책임져야 해요.

---

## 11. 바로 써먹는 프롬프트 설계 템플릿

아래 내용을 복사해서 웹사이트 기획, 수업 피드백, AI 기능 설계에 맞게 바꿔 써 보세요.

```text
[목표]
이번 작업에서 반드시 해결해야 할 문제는 ...이다.

[대상과 배경]
이 결과를 보는 사람은 ...이고, 현재 상황은 ...이다.

[입력 자료]
아래 자료에서 확인되는 정보만 근거로 사용한다.
자료: ...

[판단 기준]
1. ...을 우선한다.
2. ...과 ...을 구분한다.
3. ...을 근거로 설명한다.

[하지 말아야 할 일]
- 제공하지 않은 사실을 만들어내지 않는다.
- 확인한 사실과 제안을 섞지 않는다.

[출력 형식]
1. 핵심 결론
2. 근거
3. 개선 제안
4. 추가 확인이 필요한 사항

[품질 확인]
응답 전에 필수 항목이 모두 포함됐는지 점검한다.
```

이 템플릿은 출발점이에요. 쓰는 모델·도구·작업에 맞춰 줄이거나 더 구체적으로 바꾸면 돼요.

## 12. 20분 실습: 같은 과제, 다른 컨텍스트

### 준비

학생이 리뉴얼할 웹사이트 하나를 골라요. 실제 사이트 화면을 보거나, 핵심 구조를 텍스트로 정리해 둬요.

### 실습 A — 정보 없이 요청하기 (5분)

> "이 회사의 웹사이트 메인 화면을 기획해 줘."

결과를 저장하고 이런 걸 확인해요.

- 목표를 AI가 추측했나?
- 확인하지 않은 정보를 만들어 냈나?
- CTA가 사용자 목적과 연결되나?

### 실습 B — 기준 추가하기 (5분)

목표·타깃·현재 문제·우선할 행동·필수 섹션·출력 형식을 정리해서 다시 요청해요.

### 실습 C — 근거 추가하기 (5분)

실제 웹사이트에서 관찰한 구조나 콘텐츠 목록을 함께 주고, **관찰 사실 / 추정 / 개선 제안**을 나눠 달라고 해요.

### 결과 비교 (5분)

| 비교 항목 | A | B | C |
|---|---|---|---|
| 사용자 목표가 분명한가? |  |  |  |
| 근거가 제시되었는가? |  |  |  |
| 사실과 추정이 구분되는가? |  |  |  |
| 실제 수정에 쓸 수 있는가? |  |  |  |

여기서 배울 건 **"프롬프트가 길면 무조건 좋다"가 아니에요.** **판단에 필요한 정보와 기준을 넣었을 때 결과가 어떻게 달라지는지** 직접 보는 거예요.

## 13. 내가 어디까지 알아야 할까요?

| 학습 수준 | 알아야 할 내용 |
|---|---|
| 지금 꼭 알기 | 목표·배경·기준·제약·출력 형식 구분하기 |
| AI 서비스 만들 때 | 지시와 사용자 데이터의 역할, 구조화 출력, 검증과 테스트 |
| 서비스가 커지면 | RAG, 컨텍스트 선별, 프롬프트 인젝션 방어, 자동 평가 |
| 심화 과정 | 모델별 메시지 우선순위, 토큰 예산 설계, 평가 파이프라인 |

프롬프트 비법을 다 외울 필요는 없어요. **좋은 결과를 정의하고, 자료를 고르고, 결과를 검증하는 능력**이 훨씬 오래가요.

---

## 오늘의 핵심 정리

- **프롬프트 = 작업 지시서** → 목표·기준·제약·출력 형식까지 구체적으로 쓰기
- **컨텍스트 = AI가 판단할 근거** → 많이 주기보다 필요한 것만 골라 주기
- **역할 지시보다 근거와 판단 기준이 먼저** → 자신감 있는 문장을 사실로 착각하지 않기
- **품질은 테스트로 확인하기** → 한 번 잘 나온 답보다 여러 입력에서 기준을 지키는지 보기
- **프롬프트로 풀 문제와 코드로 풀 문제 나누기!** 데이터·권한·결제는 무조건 코드 검증

### 스스로 확인하는 질문

- 프롬프트와 컨텍스트의 차이를 한 문장으로 설명할 수 있을까?
- AI가 없는 사실을 지어내지 않게 하려면 자료와 지시를 어떻게 구성할까?
- 같은 요청에서 결과가 달라졌을 때 무엇을 테스트해야 할까?
- 내 서비스에서 반드시 코드로 검증해야 할 건 무엇일까?
