## 1. AI는 왜 시험을 봐야 할까?

AI에게 “웹사이트의 문제점을 찾아줘”라고 했다고 생각해 보자.

AI는 이렇게 답할 수 있다.

> “사용자 경험을 개선하고 직관적인 디자인을 적용하면 좋겠습니다.”

말은 자연스럽다. 하지만 어느 화면의 무엇이 문제인지, 어떤 사용자가 불편한지, 어떻게 고칠지는 알 수 없다.

이 답변을 **유창하다**고는 할 수 있어도, **실무에 쓸 수 있다**고 하기는 어렵다.

AI 서비스도 마찬가지다. 누군가 답변을 보고 “좋네요”라고 하는 것만으로는 품질을 판단하기 어렵다. 어떤 조건에서 잘 작동하고, 어디서 틀리는지를 확인해야 한다.

이렇게 AI의 결과를 정해 놓은 기준과 사례로 검사하는 일을 **평가(Evaluation, 줄여서 Eval)**라고 한다.

### 오늘의 핵심

**AI를 잘 만드는 일은 좋은 프롬프트를 작성하는 것에서 끝나지 않는다. 좋은 결과가 무엇인지 정의하고, 실제로 그렇게 나오는지 반복해서 확인해야 한다.**

## 2. 일반 프로그램의 테스트와 AI 테스트는 뭐가 다를까?

일반적인 로그인 기능을 떠올려 보자.

- 올바른 비밀번호를 입력하면 로그인이 성공해야 한다.
- 틀린 비밀번호를 입력하면 로그인이 실패해야 한다.
- 빈 입력창을 제출하면 오류 안내가 보여야 한다.

기대 결과가 꽤 명확하다.

하지만 AI에게 “이 학생의 웹사이트 리뉴얼 기획을 평가해 줘”라고 하면 어떨까?

같은 자료를 주어도 문장과 표현이 조금씩 달라질 수 있다. 두 답변이 서로 다르다고 무조건 하나가 틀렸다고 볼 수도 없다.

그래서 AI 평가는 보통 두 종류를 함께 본다.

| 구분 | 검사하는 것 | 예시 |
|---|---|---|
| **정답이 비교적 명확한 항목** | 규칙·형식·사실 | 필수 항목 5개가 모두 있는가? JSON 형식이 유효한가? 존재하지 않는 출처를 만들지 않았는가? |
| **판단이 필요한 항목** | 적절성·도움됨·문장 품질 | 설명이 초보자에게 이해되는가? 개선 제안이 문제와 연결되는가? |

**둘 중 하나만 검사하지 않는 것**이 중요하다. 문장이 자연스러워도 사실이 틀릴 수 있고, 필수 항목을 모두 채워도 쓸모없는 답변일 수 있기 때문이다.

## 3. ‘좋은 답변’을 먼저 정의하자

찐망고 사주풀이의 궁합 해설을 예로 들어 보자.

가상의 테스트 입력:

> A는 문제가 생기면 해결책부터 제시하고, B는 먼저 자신의 기분을 정리할 시간이 필요한 관계를 설명해 줘.

### 답변 A

> 두 사람은 서로 다르지만 이해하고 배려하면 좋은 관계를 이어갈 수 있어요.

### 답변 B

> A는 상대가 힘들어 보이면 빨리 해결해 주고 싶어요. 그런데 B는 해결책을 듣기 전에 자기 마음을 정리하고 싶을 수 있죠. A는 ‘왜 내 도움을 거절하지?’ 하고 서운해지고, B는 ‘지금은 해결보다 내 말을 들어줬으면 좋겠어’라고 느낄 수 있어요. 그래서 A가 먼저 “지금은 들어주는 게 좋을까, 같이 방법을 찾을까?”라고 물어보면 도움이 될 수 있어요.

어느 쪽이 더 나을까? 이번 서비스의 목표가 **관계의 행동 차이를 구체적으로 이해시키는 것**이라면 B가 더 적합해 보인다.

그렇다면 평가 기준도 구체적으로 만들 수 있다.

1. **차이를 설명했는가?** 두 사람의 행동 방식이 구별되는가?
2. **원인과 반응이 이어지는가?** 왜 서운함과 답답함이 생기는지 설명하는가?
3. **말이 쉬운가?** 어려운 추상어를 남발하지 않는가?
4. **실천할 방법이 있는가?** 바로 써 볼 수 있는 대화나 행동이 있는가?
5. **근거 없이 단정하지 않는가?** 사주 해석 또는 사용자가 제공한 정보만으로 실제 성격과 미래를 확정하지 않는가?

마지막 5번이 중요하다. **읽기 좋은 글**과 **근거 있는 글**은 별개다. 특히 사주 해석은 검증된 심리 진단과 다르므로, 해석적 제안과 사실 진술을 혼동하지 않도록 평가해야 한다.

## 4. 평가표(Rubric)를 만들면 무엇이 달라질까?

수업에서 학생 평가표를 사용할 때를 생각해 보자.

단순히 “완성도가 좋아 보인다”가 아니라, IA가 사용자의 목적에 맞는지, 레퍼런스가 문제 해결과 연결되는지, 메인 화면의 콘텐츠 순서가 합리적인지 등을 나눠서 평가한다.

AI도 같은 방식으로 검사할 수 있다.

### 예시: AI 웹사이트 분석 결과 평가표 — 100점

| 항목 | 배점 | 확인 질문 |
|---|---:|---|
| 문제의 구체성 | 25점 | 어떤 화면·콘텐츠·사용자 행동이 문제인지 특정했나? |
| 근거 | 20점 | 관찰 자료와 주장 사이에 연결이 있나? |
| 개선안의 연결성 | 25점 | 해결책이 문제를 직접 해결하나? |
| 실행 가능성 | 15점 | 디자인 또는 퍼블리싱 단계에서 구현할 수 있나? |
| 설명의 명료성 | 15점 | 초보자도 이해할 수 있는 문장인가? |

**주의:** 이 점수는 실습을 위한 예시이며, 이미 운영 중인 학생 평가표의 배점과는 별개다. 실제 학생 채점에는 공지된 공식 기준을 그대로 적용해야 한다.

숫자만 넣어 두면 객관적일 것 같지만, 채점자마다 ‘좋음’의 기준이 다르면 결과가 흔들린다. 그래서 각 점수 구간에 **어떤 답변이 해당하는지 예시**를 붙이는 편이 좋다.

## 5. 테스트 데이터셋: 한두 번 잘했다고 끝이 아니다

프롬프트를 수정하고 같은 질문을 딱 한 번 다시 보냈다고 가정해 보자.

답이 좋아졌다면 수정에 성공한 걸까?

**아직은 모른다.** 다른 질문에서는 더 나빠졌을 수도 있기 때문이다.

그래서 평가용 질문과 기대 결과를 여러 개 모아 둔다. 이것을 **테스트 데이터셋(Dataset)**이라고 한다.

| 테스트 ID | 상황 | 기대하는 결과 | 특히 확인할 오류 |
|---|---|---|---|
| T01 | 관계에서 해결 방식이 다름 | 행동 차이를 구체적으로 설명 | 두 인물의 입장 뒤바뀜 |
| T02 | 관계에서 갈등이 거의 없음 | 억지로 갈등을 만들어 내지 않음 | 없는 문제를 단정 |
| T03 | 사용자 정보가 부족함 | 모르는 점을 인정 | 세부 성격 지어냄 |
| T04 | 설명을 짧게 요청 | 핵심만 간결하게 작성 | 지나치게 긴 답변 |
| T05 | 출력 형식을 JSON으로 지정 | 정해진 필드만 반환 | 파싱 오류 |
| T06 | 서로 반대되는 지시가 있음 | 상위 규칙과 정책을 우선 | 사용자 지시로 필수 규칙 무시 |

처음부터 1,000개를 만들 필요는 없다. **실제로 자주 발생한 오류 10~20개부터** 모아도 충분히 시작할 수 있다.

### 테스트 데이터를 만드는 쉬운 방법

1. 그동안 AI가 잘못 답했던 사례를 고른다.
2. 개인정보는 제거하거나 가명으로 바꾼다.
3. 당시 입력과 기대했던 결과를 기록한다.
4. 다시 발생하면 안 되는 오류를 표시한다.
5. 프롬프트나 모델을 바꿀 때 같은 사례를 다시 돌린다.

AI 서비스에서 오류 사례는 실패 기록이 아니라 **다음 버전을 검증하는 자산**이 된다.

## 6. 세 가지 평가 방법

### 방법 A. 규칙으로 검사하기

예: JSON 필수 필드, 최대 글자 수, 금지된 표현, 빈 값 여부를 코드로 검사한다.

```python
# 간단한 예시: AI 응답이 필요한 구조를 갖췄는지 확인
required = ["summary", "difference", "suggestion"]
response = {
    "summary": "두 사람은 문제에 접근하는 순서가 달라요.",
    "difference": "A는 해결부터, B는 감정 정리부터 시작해요.",
    "suggestion": "먼저 원하는 도움의 형태를 물어보세요."
}

passed = all(isinstance(response.get(k), str) and response[k].strip() for k in required)
print(passed)  # True
```

**장점:** 빠르고 재현 가능하다.  
**한계:** 문장이 정말 좋은지는 판단하기 어렵다.

### 방법 B. 사람이 직접 평가하기

실제 사용자나 분야 전문가가 결과를 보고 기준표에 따라 판단한다.

**장점:** 뉘앙스와 유용성을 볼 수 있다.  
**한계:** 시간과 비용이 들고 평가자마다 의견이 다를 수 있다.

### 방법 C. AI가 다른 AI의 답변을 평가하기 (LLM-as-a-Judge)

평가용 AI에게 기준표와 답변을 주고, 각 항목의 충족 여부를 판단하게 한다.

**장점:** 많은 답변을 빠르게 검토할 수 있다.  
**한계:** 평가용 AI도 틀리거나 특정 문체를 선호할 수 있다. 자기 답변을 평가하게 하면 편향이 생길 수도 있다.

**실무 추천:** 형식은 코드로 검사하고, 의미와 문장 품질은 AI로 1차 평가한 뒤, 중요한 결과와 애매한 사례는 사람이 확인한다.

## 7. 프롬프트를 고쳤는데 진짜 좋아졌는지 비교하기

기존 프롬프트를 **A**, 수정한 프롬프트를 **B**라고 하자.

같은 테스트 20개를 두 버전 모두에 적용한다.

| 지표 | A | B |
|---|---:|---:|
| 필수 항목 충족 | 15/20 | 19/20 |
| 인물 혼동 | 4/20 | 1/20 |
| 근거 없는 단정 | 5/20 | 2/20 |
| 사람이 ‘이해하기 쉽다’고 평가 | 12/20 | 17/20 |

*위 수치는 방법 설명을 위해 만든 가상의 예시다.*

이 결과라면 B가 개선되었다고 판단할 근거가 생긴다. 다만 표본이 작고 AI 출력에는 변동성이 있으니, 중요한 변경이라면 여러 번 반복하고 다른 종류의 입력도 확인하는 편이 좋다.

하나 더 기억하자. **평균 점수만 보면 안 된다.** 전체 점수는 좋아졌어도 특정 사용자에게 위험한 오류가 더 많이 발생했다면 배포를 멈춰야 할 수도 있다.

## 8. ‘회귀 테스트’가 중요한 이유

**회귀(Regression)**란 새로 고친 뒤에 예전에 잘되던 기능이 다시 망가지는 현상을 말한다.

예를 들어 궁합 해설의 문장을 자연스럽게 만들려고 프롬프트를 수정했더니:

- 문장은 좋아졌는데 두 사람의 역할이 뒤바뀌고,
- 문장은 짧아졌는데 필수 카드가 사라지고,
- 예시가 다양해졌는데 입력 정보에 없는 성격을 만들어 낸다면?

새 기능을 추가한 게 아니라 다른 곳에 오류를 만든 셈이다.

그래서 수정할 때마다 **이번에 고친 문제 + 이전에 잘되던 문제**를 함께 확인해야 한다. 이것이 AI 서비스에서도 회귀 테스트가 필요한 이유다.

## 9. RAG 서비스는 무엇을 평가해야 할까?

앞에서 배운 RAG를 떠올려 보자.

RAG 답변이 틀렸다고 해서 항상 생성 모델의 문제는 아니다.

```mermaid
flowchart TD
  A[사용자 질문] --> B[관련 문서 검색]
  B --> C{올바른 자료를 찾았나?}
  C -->|아니오| D[검색·청킹·인덱싱 점검]
  C -->|예| E[자료를 근거로 답변 생성]
  E --> F{근거에 맞게 답했나?}
  F -->|아니오| G[프롬프트·인용·생성 단계 점검]
  F -->|예| H[최종 품질 확인]
```

여기서는 **검색 품질**과 **답변 품질**을 나누어 측정한다.

| 평가 단계 | 질문 |
|---|---|
| 검색 정확도 | 필요한 문서를 찾아왔나? |
| 검색 누락 | 정답에 필요한 문서를 빠뜨리지 않았나? |
| 근거 충실성 | 자료에 없는 주장을 새로 만들어 내지 않았나? |
| 답변 유용성 | 사용자가 실제로 필요한 답을 받았나? |
| 출처 검증 | 표시된 링크가 실제 근거를 가리키나? |

찐망고 레퍼런스에서 “브랜드 스토리를 강조한 히어로 섹션을 찾아줘”라고 질문했을 때, AI가 멋진 설명을 했어도 전혀 다른 유형의 화면을 찾아왔다면 **검색 결과부터** 확인해야 한다.

## 10. 에이전트는 최종 답변만 보면 안 된다

AI 에이전트가 GitHub에 파일을 저장했다고 말한다고 해 보자.

말로만 “저장했습니다”라고 답했다면 성공이 아니다. 실제로 파일이 생겼는지 확인해야 한다.

에이전트 평가는 다음까지 살펴본다.

- 요청한 도구를 올바르게 사용했나?
- 허용되지 않은 변경은 하지 않았나?
- 실패가 났을 때 적절히 멈추거나 재시도했나?
- 사람의 승인이 필요한 단계에서 승인받았나?
- **최종 결과가 실제 환경에서 확인되는가?**

예를 들어 학생의 코드를 수정하는 에이전트라면 ‘수정 완료’라는 대답보다 **실제 변경된 파일과 테스트 결과**가 중요하다.

---

## 11. 서비스 운영에서 꼭 추적할 지표

평가 점수만 높다고 좋은 서비스는 아니다.

| 분류 | 예시 지표 | 왜 볼까? |
|---|---|---|
| 품질 | 테스트 통과율, 오류 유형 | 결과가 개선되는지 |
| 안정성 | 요청 실패율, JSON 파싱 실패율 | 기능이 멈추지 않는지 |
| 속도 | 응답 시간, 첫 응답까지 시간 | 사용자가 기다리다 떠나지 않는지 |
| 비용 | 요청당 토큰, 요청당 비용 | 서비스가 지속 가능한지 |
| 사용자 경험 | 재생성·수정 요청 비율 | 결과가 실제로 만족스러운지 |

**주의:** 재생성 버튼을 많이 누르는 이유는 불만족일 수도 있고, 여러 결과를 비교하려는 사용 습관일 수도 있다. 하나의 지표만으로 만족도를 단정하면 안 된다.

또 실제 사용자 데이터로 평가할 때는 개인정보를 익명화하고, 필요 이상의 원문을 로그에 남기지 않아야 한다.

## 12. 이제 직접 해 보자 — 20분 실습

### 실습 A. AI 웹사이트 분석의 평가 기준 만들기 (7분)

AI에게 다음 질문을 해 본다.

> 웹사이트의 메인 화면을 분석하고 개선안을 제시해 줘.

대답을 받은 뒤 아래 세 가지를 찾는다.

1. 사용자와 사용 목적이 구체적인가?
2. 문제와 해결책이 한 쌍으로 연결되는가?
3. 실제로 화면에서 수정할 수 있는 내용인가?

**질문:** ‘좋은 답변’이라고 판단할 수 있는 최소 조건을 3개 적어 보자.

### 실습 B. 프롬프트 A/B 비교하기 (8분)

**A 프롬프트**

> 이 웹사이트를 분석해 줘.

**B 프롬프트**

> 이 웹사이트를 처음 방문한 고객이 상품을 찾고 구매하기까지의 흐름을 기준으로 분석해 줘. 확인 가능한 화면 정보만 근거로 사용하고, 각 문제마다 사용자 영향과 수정 방향을 함께 적어 줘. 확인하지 못한 내용은 추측이라고 구분해 줘.

같은 웹사이트 자료를 두 프롬프트에 넣고, 직접 만든 평가 기준으로 비교한다. **B가 무조건 이긴다는 보장은 없다.** 중요한 것은 어떤 점에서 좋아지고, 어떤 점에서는 부족한지 설명하는 것이다.

### 실습 C. 실패 사례 저장하기 (5분)

오늘 AI 답변에서 발견한 오류 하나를 기록해 보자.

```json
{
  "id": "test-001",
  "task": "웹사이트 개선안 작성",
  "input": "제공된 메인 화면에서 문제를 찾아줘",
  "expected": "화면에서 확인한 근거와 문제, 개선안을 연결할 것",
  "failure_type": "근거 없는 일반론",
  "reviewer_note": "실제 화면 요소를 하나도 특정하지 않음"
}
```

이 기록이 모이면 내가 만든 AI 서비스만의 테스트 데이터셋이 된다.

## 13. 지금 어디까지 알아야 할까?

| 지식 | 지금 중요도 | 이유 |
|---|---|---|
| 좋은 답변의 조건 정하기 | **매우 중요** | AI를 쓰는 누구에게나 필요 |
| 테스트 사례 모으기 | **매우 중요** | 프롬프트 개선을 검증할 수 있음 |
| A/B 비교와 회귀 테스트 | **중요** | 서비스 품질이 다시 나빠지는 걸 막음 |
| RAG 검색과 답변 별도 평가 | **필요할 때 중요** | 문서 검색 서비스를 만들 때 필요 |
| LLM 평가 자동화 코드 | 나중에 | 테스트가 많아진 뒤 도입해도 됨 |
| 복잡한 통계와 벤치마크 설계 | 심화 | 대규모 운영·연구에서 필요 |

### 이 장을 한 문장으로 정리하면

> **프롬프트는 AI에게 무엇을 하라고 알려 주고, 평가는 AI가 정말 그 일을 해냈는지 확인한다.**
