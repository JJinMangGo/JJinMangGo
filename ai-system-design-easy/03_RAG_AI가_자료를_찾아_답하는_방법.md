# 03. RAG — AI가 모르는 자료를 찾아 답하는 방법

- 난이도: ★★☆☆☆ — 개념을 이해하면 충분
- 예상 학습 시간: 25~35분
- 먼저 읽기: [02. 프롬프트와 컨텍스트 설계](02_프롬프트와_컨텍스트_설계.md)

> 이 글은 원문을 옮긴 번역본이 아니라, 원문의 핵심 개념을 초보자 눈높이에 맞춰 새로 풀어 쓴 **독립 해설**이에요. 기술 선택 기준과 실제 구현 방식은 서비스 규모와 모델에 따라 달라질 수 있어요.

## 이 장을 읽고 나면

- RAG가 무엇인지 한 문장으로 설명하기
- PDF를 대화창에 올리는 것과 RAG 시스템을 만드는 것의 차이 알기
- **청킹(Chunking)**, **임베딩(Embedding)**, **리랭킹(Reranking)**이 왜 필요한지 이해하기
- RAG가 필요할 때와 굳이 안 써도 될 때 구분하기
- AI가 답을 지어내지 않도록 검색·권한·출처·평가를 어떻게 설계할지 생각해 보기

## 1. AI가 모르는 질문을 받았을 때

학생이 이렇게 물어봤어요.

> "우리 수업 2차 평가에서 반응형 웹은 몇 점이고, 어떤 기준으로 평가해요?"

일반 AI 모델은 그 수업의 실제 평가표를 **학습한 적이 없을 수 있어요.** 그런데도 "20점입니다"라고 그럴듯하게 답할 수 있죠. 이게 진짜 문제가 되는 순간은 **사실처럼 보이는 오답이 학생의 행동을 바꿀 때**예요.

그렇다면 AI가 추측하지 말고, 실제 평가표를 찾아 읽은 다음 답하게 하면 어떨까요?

> "제공된 평가표에 따르면 반응형은 15점이며, PC·Tablet·Mobile에 맞춰 화면을 구성했는지를 평가합니다."

이렇게 AI가 *평가표에서 관련 내용을 먼저 찾은 다음* 답하게 만드는 방식이 **RAG**예요.

**RAG = Retrieval-Augmented Generation**, 우리말로는 보통 **검색 증강 생성**이라고 해요.

- **Retrieval(검색):** 관련 자료를 찾아온다
- **Augmented(증강):** 찾은 자료를 질문과 함께 AI에게 건넨다
- **Generation(생성):** AI가 자료를 참고해 답을 쓴다

**한 줄로 기억하기:** *AI 기억만 믿지 말고, 필요한 자료를 찾아 펼쳐 준 다음 답하게 하는 구조!*

## 2. RAG는 '책을 외운 AI'가 아니라 '책을 찾아보는 AI'

아래 세 가지를 구분하면 쉬워요.

| 구분 | 비유 | 특징 |
|---|---|---|
| 모델의 사전 학습 | 여러 책을 공부한 사람 | 아는 건 많지만 최신·정확하다고 보장되지 않음 |
| 파인튜닝(Fine-tuning) | 특정 방식으로 답하도록 추가 훈련 | 말투·형식·작업 패턴을 익히게 할 때 활용 |
| RAG | 필요한 책에서 관련 페이지를 찾아 펼쳐 주기 | 외부 자료를 근거로 답하게 도와줌 |

핵심은 RAG가 **AI 모델을 새로 훈련시키는 게 아니라는 점**이에요.

예를 들어 평가 기준이 바뀌었다면, RAG에서는 **검색 대상 문서를 최신 버전으로 바꾸고** 색인만 갱신하면 돼요. AI 내부 지식을 다시 훈련시킬 필요가 없어요.

다만 문서를 바꿨다고 답이 저절로 정확해지진 않아요. 최신 문서가 실제 검색 결과에 잡히는지 꼭 확인해야 해요.

## 3. RAG는 이렇게 움직여요

```mermaid
flowchart TD
    A[학생이 질문한다] --> B[질문과 관련된 자료 검색]
    C[평가표·수업안내·FAQ] --> B
    B --> D[관련 문서 조각 선택]
    D --> E[질문 + 근거 자료를 AI에게 전달]
    E --> F[AI가 근거에 맞춰 답변 작성]
    F --> G[답변 + 출처 표시]
```

여기서 중요한 건 **검색된 문서 조각이 실제로 답변에 쓰였느냐**예요. 검색 결과가 틀렸다면, 생성 모델이 아무리 똑똑해도 틀린 답을 할 수밖에 없어요.

### 실제 화면으로 바꿔 생각해 보기

사용자 화면에는 이 세 가지만 있어도 충분할 수 있어요.

1. **질문 입력창:** "반응형 웹 평가 기준 알려줘."
2. **답변 영역:** "반응형 웹은 15점이며…"
3. **출처 영역:** "출처: 2차 평가표, 반응형 항목"

출처는 문서 제목만 보여 주기보다, **누르면 원본의 해당 위치로 바로 갈 수 있게** 만드는 게 좋아요.

## 4. PDF를 올리면 그게 RAG일까요?

**꼭 그렇지는 않아요.** 겉보기엔 비슷해도 안에서 처리하는 방식이 다를 수 있거든요.

### A. 채팅창에 작은 PDF 하나를 올린 경우

AI 서비스가 파일 내용을 읽어서 대화 컨텍스트에 넣을 수도 있고, 서비스 내부 검색 도구를 쓸 수도 있어요. **파일을 올렸다는 것만으로 RAG라고 단정하면 안 돼요.**

- 장점: 바로 질문할 수 있어서 간편함
- 단점: 파일이 많아지고 버전이 쌓이면 관리가 어려워짐

### B. 우리 서비스에 문서 검색 기능을 만든 경우

1. 여러 문서를 모은다
2. 검색하기 좋게 처리하고 색인한다
3. 사용자가 질문하면 관련 문서만 찾는다
4. 찾은 부분을 AI에게 넘긴다
5. 근거와 함께 답한다

이렇게 **반복해서 쓸 수 있는 검색+답변 시스템**을 보통 RAG 시스템이라고 불러요.

그리고 **무조건 RAG를 만들 필요는 없어요.** 문서가 몇 개 안 되고 수정도 거의 없다면, 필요한 내용을 프롬프트에 바로 넣는 게 더 간단할 수 있어요.

## 5. 문서를 잘라서 보관해요: 청킹(Chunking)

100페이지짜리 수업 자료에서 딱 한 줄을 찾아야 한다고 해 볼게요. 매번 100페이지를 통째로 AI에게 주면 번거롭고 비용도 커지겠죠.

그래서 문서를 의미 있는 크기로 나눠서 보관해요. 이걸 **청킹(Chunking)**이라고 해요.

예를 들어 평가표를 이렇게 나눌 수 있어요.

- 조각 A: UI 구조 설계 / 15점 / 세부 기준
- 조각 B: Figma 기능 활용 / 20점 / 세부 기준
- 조각 C: HTML·CSS / 20점 / 세부 기준
- 조각 D: 반응형 웹 / 15점 / 세부 기준

반응형에 대한 질문이라면 **조각 D부터 찾으면** 되겠죠.

### 잘못 나누면 생기는 일

글자 수로만 기계적으로 자르면 이런 일이 생겨요.

> 조각 1: "반응형 웹은 PC, 태블릿, 모바일에 맞춰…"  
> 조각 2: "…구성할 수 있는가? (15점)"

질문에 필요한 문장과 점수가 따로 떨어져 버렸어요. 이러면 AI가 근거를 온전히 찾지 못할 수 있어요.

**실무 메모:** 청킹은 글자 수를 정하는 일이 아니라 **질문에 답할 정보가 한 덩어리로 남도록 나누는 일**이에요. 제목, 표 머리글, 문서 버전도 같이 남겨 두면 좋아요.

## 6. 단어가 달라도 뜻이 비슷하면 찾을 수 있을까요? 임베딩(Embedding)

학생은 이렇게 물어봤어요.

> "핸드폰에서 화면이 깨지면 몇 점 깎여요?"

그런데 평가표에는 "모바일 환경을 고려한 반응형 레이아웃 설계"라고 적혀 있어요.

문장은 다르지만 두 문장이 **비슷한 문제를 말하고 있다는 걸** 알아채야 하죠.

여기서 **임베딩(Embedding)**이 등장해요. 문장이나 문서의 의미적 특징을 숫자 벡터로 바꿔서, 뜻이 비슷한 문서를 찾도록 도와주는 방식이에요.

- "모바일에서 화면 깨짐"
- "작은 화면에 맞는 반응형 구성"

단어가 똑같지 않아도 의미 기반 검색에서는 가까운 결과로 잡힐 수 있어요.

그런데 의미 검색만으로는 부족할 때도 있어요. **정확한 모델명, 제품 코드, 학생 과제명, CSS 속성명**처럼 글자 자체가 중요한 경우요.

그래서 실무에서는 **키워드 검색 + 의미 검색**을 합친 **하이브리드 검색(Hybrid Search)**도 고려해요.

| 질문 | 더 중요할 수 있는 검색 방식 |
|---|---|
| "모바일에서 깨지는 문제" | 의미 기반 검색 |
| "`flex-basis`와 `width` 차이" | 정확한 키워드 + 의미 검색 |
| "평가표에서 15점 항목" | 키워드·숫자 매칭 |
| "로그인 화면에서 접근성을 어떻게 평가해?" | 의미 검색 + 문서 필터 |

어떤 검색 방식을 쓸지는 **실제 질문으로 테스트해 보고** 정해야 해요.

## 7. 검색했다고 끝이 아니에요: 리랭킹(Reranking)

관련 자료 10개를 찾았는데, 제일 중요한 문서가 8등으로 나왔다고 해 볼게요.

상위 3개만 AI에게 넘긴다면, **정답 문서는 검색됐는데도 답변에는 못 들어갈 수 있어요.**

리랭킹은 이미 찾은 후보를 **질문과 얼마나 관련 있는지 기준으로 다시 정렬**하는 과정이에요.

> 검색 = 후보를 넓게 모으는 일  
> 리랭킹 = 그중 질문에 가장 맞는 후보를 다시 고르는 일

다만 리랭킹에도 추가 비용과 시간이 들어요. 간단한 서비스라면 처음부터 넣기보다 **검색 실패 사례를 모아 본 뒤에 도입을 판단**하는 게 좋아요.

## 8. AI는 어디서 틀릴까요?

RAG를 쓴다고 환각(사실과 다른 답)이 사라지진 않아요. 실패 원인을 단계별로 나눠 보면 고치기가 훨씬 쉬워요.

| 문제가 생긴 단계 | 예시 | 먼저 점검할 것 |
|---|---|---|
| 문서 수집 | 구버전 평가표만 들어 있음 | 최신 문서 여부·갱신 방식 |
| 문서 분리 | 제목과 점수가 다른 조각으로 분리됨 | 청킹 방식·문서 구조 |
| 검색 | 해당 조각을 찾지 못함 | 키워드/의미 검색·검색 필터 |
| 결과 선택 | 중요한 자료가 순위에서 밀림 | 리랭킹·선택 개수 |
| 답변 생성 | 찾은 근거에 없는 내용을 덧붙임 | 근거 기반 지침·답변 검증 |
| 출처 표시 | 엉뚱한 페이지를 출처로 표시함 | 인용 대상과 원문 위치 일치 여부 |

문제가 생겼을 때 **무조건 프롬프트부터 고치면 안 되는 이유**가 여기 있어요. 검색이 틀렸다면 프롬프트만 바꿔서는 해결이 안 될 수 있거든요.

## 9. 긴 컨텍스트가 있으면 RAG는 필요 없지 않나요?

요즘 모델은 한 번에 꽤 많은 텍스트를 처리해요. 그럼 필요한 문서를 다 넣으면 되지 않을까요?

자료가 적다면 실제로 그게 더 편할 수 있어요. 하지만 규모가 커지면 네 가지를 생각해야 해요.

1. **비용:** 질문마다 방대한 문서를 계속 보내면 입력 비용이 커짐
2. **속도:** 읽어야 할 자료가 많아지면 응답이 느려짐
3. **최신성:** 자주 바뀌는 내용을 매번 관리해야 함
4. **접근 권한:** 사용자마다 볼 수 있는 문서가 다를 수 있음

그래서 **긴 컨텍스트 vs RAG**는 누가 이기냐의 문제가 아니에요.

- **자료 적고 질문도 적다면** → 문서를 그대로 넣는 방법부터 검토하기
- **자료 많고, 자주 바뀌고, 사용자도 다양하다면** → 검색 구조와 권한 관리까지 고려하기

원문 가이드에 나오는 문서량별 기준값은 환경마다 달라서, **절대적인 기준선처럼 쓰지 않는 게 좋아요.**

## 10. 찐망고 사주풀이에 RAG를 적용한다면?

여기서는 **실제 서비스에 RAG가 이미 들어가 있다는 뜻이 아니라**, 적용 가능성을 생각해 보는 예시예요.

### 지금처럼 프롬프트와 데이터를 넘기는 방식

사용자가 생년월일과 시간을 입력하면, 서비스가 사주 계산 결과와 해석 지침을 AI에 넘길 수 있어요.

이 경우 핵심은 **계산 데이터의 정확성, 해석 규칙, 출력 검증**이에요. 꼭 RAG가 필요하진 않죠.

### 만약 '명리학 자료 검색 기능'을 추가한다면

사용자가 "경금 일간이 인월에 태어나면 어떤 해석 차이가 있나요?"라고 묻는다고 해 볼게요.

- 검색 대상으로 **사용 권한을 확보한 명리학 자료** 모으기
- 질문에 맞는 해설 찾아오기
- AI가 서로 다른 해석 관점이 있다는 걸 구분해서 설명하기
- 참고 자료의 제목과 해당 부분을 출처로 보여 주기

이럴 때는 RAG가 의미가 생겨요. 다만 명리학 해석은 검증된 자연과학적 사실과 구분해야 해서, **출처가 있다고 해석 자체가 객관적으로 입증되는 건 아니에요.**

### 찐망고 레퍼런스 서비스에 적용한다면?

Hero, CTA, 브랜드 스토리 같은 섹션마다 **직접 기록한 분석 메모와 태그**가 있다면, 이런 질문에 답하게 만들 수 있어요.

> "회원가입 유도를 잘 설계한 국내 웹사이트 사례 3개 찾아줘."

RAG가 저장된 분석 메모를 바탕으로 사례를 추천하는 거죠. 그런데 이미지 캡처만 있고 설명이나 태그가 없다면, **무엇을 기준으로 검색할지**부터 설계해야 해요.

이럴 때 중요한 건 모델 성능보다 **좋은 원천 자료를 얼마나 잘 구조화해 뒀느냐**일 수 있어요.

## 11. 학생용 실습: 평가표를 읽는 AI 만들기 전에

서버를 개발하지 않아도 RAG 설계는 연습할 수 있어요.

### 준비물

공개해도 되는 **가상 평가표** 1개, 예상 질문 5개, 종이 또는 Figma.

예시 질문:

1. "모바일 레이아웃은 몇 점인가요?"
2. "Figma 컴포넌트도 평가에 들어가나요?"
3. "작업 결과물이 디자인 시안과 달라도 괜찮나요?"
4. "지각하면 몇 점이 깎이나요?"
5. "CSS가 아닌 JavaScript로 작성해도 점수를 주나요?"

### 실습 순서

1. 평가표를 4~6개의 의미 있는 조각으로 나누기
2. 질문마다 찾아야 할 **정답 조각** 표시하기
3. 답을 만들 때 **문서에 있는 것 / 없는 것** 구분하기
4. 근거가 없는 질문에는 "이 평가표에서 확인할 수 없습니다"라고 답하도록 정하기
5. 답변 아래에 자료 제목과 항목 붙이기

### 관찰 포인트

- 근거 있는 답을 했나?
- 질문이 바뀌어도 맞는 조각을 찾나?
- 평가표에 없는 내용을 지어내지 않았나?
- 학생이 출처를 눌러서 확인할 수 있나?

이 실습이 좋은 이유는 **프롬프트 작성 실력뿐 아니라 정보 구조를 설계하는 능력**까지 같이 기를 수 있어서예요.

## 12. 운영한다면 꼭 생각할 세 가지

### ① 권한: 검색하면 안 되는 자료는 검색하지 않기

교사만 봐야 하는 상담 기록이나 개인 정보를 학생용 검색 대상에 넣으면 안 돼요. **검색하기 전에 사용자 권한부터 확인**해야 하고요. "이 자료는 보여 주지 마"라는 프롬프트만으로 접근 권한을 지키려고 하면 안 돼요.

### ② 출처: AI의 문장이 아니라 원본을 확인할 수 있게

출처는 신뢰를 높여 주지만, **출처 제목이 붙었다고 답이 정확해지는 건 아니에요.** 답변 문장과 인용된 원문 내용이 실제로 맞는지 확인해야 해요.

### ③ 평가: 그럴듯함보다 정답 검색률 보기

테스트 질문 20개를 정하고, 이런 항목을 기록해 보세요.

- 정답이 들어 있는 문서를 검색했나?
- 답변이 근거 범위를 벗어났나?
- 모르는 질문에 모른다고 했나?
- 답변 시간이 적절한가?
- 수정된 문서가 반영됐나?

## 13. 내가 어디까지 알아야 할까요?

| 개념 | 지금 필요한 수준 | 더 깊이 배울 때 |
|---|---|---|
| RAG | 왜 검색을 붙이는지 설명 가능 | 파이프라인 직접 구축 |
| 청킹 | 문서 분리 방식이 품질에 영향을 줌을 이해 | 조각 크기·중첩 비교 실험 |
| 임베딩 | 의미로 비슷한 문서를 찾는 원리 이해 | 모델별 검색 성능 비교 |
| 하이브리드 검색 | 키워드+의미를 함께 쓰는 이유 이해 | 검색 점수 결합 방식 |
| 리랭킹 | 검색 결과를 다시 정렬한다는 점 이해 | 속도·정확도 최적화 |
| 벡터 DB | 임베딩 검색을 위한 저장·검색 수단임을 이해 | 색인, 필터, 운영 설계 |
| 평가 | 답변 전에 검색 품질부터 점검 | 검색·답변 평가 지표 구축 |

지금 목표는 벡터 데이터베이스를 직접 만드는 게 아니에요.  
**"어떤 자료를, 어떤 기준으로 찾아서, 어떤 근거를 AI에게 줘야 하지?"**라는 질문을 던질 수 있으면 충분해요.

## 14. 다 읽었는지 확인하는 질문

1. RAG와 파인튜닝은 무엇이 다를까?
2. PDF를 채팅창에 올렸다고 무조건 RAG라고 할 수 있을까?
3. 평가표의 점수와 기준이 다른 문서 조각에 있으면 어떤 문제가 생길까?
4. "모바일 화면 깨짐"과 "반응형 레이아웃"을 연결하는 검색은 무엇을 활용할까?
5. 정답이 없을 때 AI는 어떻게 행동해야 할까?

<details>
<summary>생각해 볼 답</summary>

1. RAG는 외부 자료를 찾아 답에 넣어 주고, 파인튜닝은 모델을 추가로 학습시켜요.
2. 아니에요. 서비스 내부 구현에 따라 달라요.
3. 정답을 못 찾거나, 일부 정보만 보고 틀리게 답할 수 있어요.
4. 임베딩 기반 의미 검색, 필요하면 키워드 검색까지 함께 써요.
5. 근거가 부족하다고 밝히고, 확인 가능한 자료를 안내하거나 추가 정보를 요청해야 해요.

## 이번 장에서 기억할 것

- **RAG** = AI가 외부 근거를 찾아서 답하게 만드는 설계 방식
- RAG 품질은 답변 문장만큼 **'무엇을 찾아왔는가'**에 달려 있음 → 답보다 검색부터 점검하기!
- 문서 몇 개뿐이라면 RAG보다 간단한 방법이 나을 수도 있음
- 권한은 프롬프트가 아니라 시스템에서 막기
